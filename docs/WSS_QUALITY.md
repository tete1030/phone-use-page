# WSS 画质诊断与独立演示

## 现象与原因

静止的文字页面也会约每秒整体变糊，再逐步恢复。2026-10-11 的独立实验使用合成的 864×1920 设置页，固定编码档位，不使用手机、公网、TURN 或网络限速，复现了同样的周期。

逐帧 SSIM 的下降与完整关键帧（IDR）重合。原编码参数同时存在以下问题：

1. 筛选器将输出降低到每秒 4、8、12 帧，但没有同步设置 x264 的帧率预算。本次 FFmpeg 实验中，原参数的编码时钟仍按探测出的默认帧率计算。
2. 每秒重新编码一次完整关键帧；详细文字的完整帧比预测帧大得多。
3. VBV 缓冲容量只有约三分之一秒，完整帧在预算不足时受到强烈压缩，后续预测帧逐步修复细节。

固定档位且没有拥塞时仍能复现，因此这次周期性问题的主要来源是编码，而不是自动切换通道或网络重连。实际网络环境仍可能另外影响画面。

## 本地修复

- 在 `x264-params` 中设置 `fps`，使码率预算与筛选后的档位帧率一致，同时保留 VFR。没有开启恒定帧率补帧。
- VBV 容量调整到两秒。它是编码器码率预算容量，不代表播放延迟或发送队列要等待两秒。
- 默认和高档的完整关键帧间隔改为两秒，低档为三秒；首次启动仍直接输出关键帧。
- 本机 RTP socket 请求 4 MiB 接收缓冲，诊断显示操作系统实际允许的大小。只调整本进程 socket，不修改系统网络配置。
- 本机 RTP 发生丢包时，丢弃受损帧及其后依赖旧参考的预测帧，等到完整关键帧后恢复输出。
- 保持分辨率、CRF、各档目标最大码率、无 B 帧设置及档位切换冷却规则。

更长的关键帧间隔意味着加入已有编码流或从丢包中恢复时，可能需要等待下一个完整关键帧。两秒或三秒是按额定帧率计算的间隔；源画面更新稀疏时，不能把它解释为严格的墙钟时间上限。

## 默认档位实测

使用真正的 `WssEncoder` 和 FFmpeg 管线，分别连续编码 45 秒，排除前两秒后对文字区域进行逐帧比较。原参数对照仅还原原来的编码参数；两路都使用改进后的本地 RTP 接收保护，避免把接收丢包混入压缩质量比较。

| 指标 | 原编码参数 | 修复参数 |
|---|---:|---:|
| 文字区域最低 SSIM | 0.8543 | 0.9925 |
| 平均 SSIM | 0.8901 | 0.9952 |
| 最大关键帧质量跌幅 | 0.0670 | 0.0033 |
| 平均 H.264 负载 | 307 kbps | 707 kbps |
| 编码首帧耗时 | 96 ms | 96 ms |
| 本机 RTP 丢帧 | 0 | 0 |

最大跌幅约降低 95%。两路均为固定档位，未发生编码重启或档位切换。独立 Chromium 浏览器通过本地 WebSocket 和项目的实际 WSS 播放器解码，完整分辨率、暂停保留末帧与重新播放均通过。

另外覆盖低档 20 秒、高档 16 秒对照：低档最低 SSIM 从 0.7970 改善为 0.9892，最大关键帧跌幅从 0.0500 改善为 0.0074；高档最低值从 0.8975 改善为 0.9947，最大跌幅从 0.0782 改善为 0.0009。三档均未记录到本机 RTP 丢包。

这些数字只描述该合成素材和测试主机。SSIM 不是所有页面的可读性保证；首帧数字不包含公网传输和浏览器显示延迟。修复使编码器实际使用更多原本允许的预算，不能把提高画质描述为零流量成本。VBV 允许短时突发，也不是网络硬性峰值上限。

## 如何运行独立 demo

在开发环境安装项目依赖和 FFmpeg，Python 环境需有 Pillow。还需要中文字体；无法自动找到字体时，用 `WSS_DEMO_FONT` 指定本机字体文件。原生安装方法见[主机准备](HOST_SETUP.md)。

```sh
npm ci
# 生成两路各 45 秒的样本，并启动独立的 localhost 演示页面。
npm run demo:wss-quality -- --seconds=45
```

命令打印随机分配的本地 URL。页面包含原参数流、修复流、参考图和逐帧质量曲线，默认显示原尺寸文字局部，也可查看完整画面。演示绑定 `127.0.0.1`，不读取部署凭据，不调用 ADB 或生产 API。

```sh
# 只生成样本和报告，不启动页面。
node --import tsx scripts/wss-quality-demo.mjs --seconds=16 --profiles=low,balanced,high

# 重用已生成样本，避免再次编码。
npm run demo:wss-quality -- --serve-only

# 验证真实浏览器能解码这两路样本。
npm run test:wss-quality
```

可选参数：`--output=目录`、`--port=端口`。环境变量：`PYTHON_PATH`、`FFMPEG_PATH`、`WSS_DEMO_FONT`；浏览器验证还支持 `CHROME_PATH` 和 `WSS_DEMO_OUTPUT`。

默认输出在 Git 忽略的 `.local/wss-quality-demo/`，包含 `report.md`、`results.json`、合成参考图、编码样本及浏览器验证结果。停止 demo 使用终端的 Ctrl+C，不会影响生产控制台。

## 验证边界与后续

已覆盖静止的密集中文、英文和数字、不同帧率档位，以及本机 RTP 丢包和序号回绕。正式发布前还应补充真实网络限速、持续滚动、复杂动画和实际设备编码器的测试；这些不应通过接管正在使用的生产手机完成。

另记录一项独立问题：当前上游 H.264 WebCodecs 解码器不保留输入包的 PTS，使用常量解码时间戳，而现有反馈读取 `VideoFrame.timestamp`。这会影响反馈延迟的可靠性；这次没有同时改动播放器反馈机制，也没有把静态 demo 当作自适应拥塞控制已验证的证据。

## 前端失败日志

WSS 连接、初始化、解码或绘制失败时，页面将诊断发送到同源 `POST /api/video/client-error`。服务端通过标准错误输出打印一行 JSON，`event` 固定为 `wss_client_error`；诊断不写数据库，也不写请求审计文件。日志含服务端 UTC 时间、客户端 IP/浏览器、页面关联摘要、视频尝试 ID、前端资源版本、失败阶段/错误码、原始异常名称/信息、H.264 codec、尺寸、字节/包/绘制/排队计数和浏览器能力。没有 Cookie、鉴权令牌、密码、堆栈、输入内容、JS 脚本、图像或原始视频数据；错误中的 URL/常见敏感字段会过滤。

| `stage` | 排查方向 |
| --- | --- |
| `socket` | 视频连接失败、关闭码、服务端拒绝或页面离线 |
| `metadata` / `packet` | 编码标识或视频包格式不符合协议 |
| `capability` / `decoder-init` | 安全上下文、`VideoDecoder`、`createImageBitmap`、`bitmaprenderer` 或解码器初始化不可用 |
| `decode` | 原始异常与 `avcCodec`，例如 H.264 配置不支持、缺少关键帧或解码失败 |
| `backpressure` | 客户端解码队列积压，检查 `queuedBytes` 与设备性能 |
| `render` | Canvas/图像转换失败，结合原始异常和浏览器版本判断 |

Docker 部署可在项目部署目录使用对应 Compose 配置查看：

```sh
docker compose logs --since 24h console | rg wss_client_error
```

也可以通过容器管理器查看控制台容器日志；原生部署查看 Node 进程的标准错误输出。日志仅受现有容器/进程日志驱动和保留策略管理，重建容器可能删除旧日志，不是额外的长期存储服务。

每次视频尝试最多上报一个失败，页面每分钟最多发送 5 条，后端每页面每分钟最多打印 10 条、全服务最多 60 条，消息体限制为 8 KiB。请求要求登录、同源、CSRF、当前页面与连接代号；不操作手机、不接管页面，也不续期五分钟无操作期限。上报等待最多五秒，不重试，上报失败不影响控制或视频通道切换；网络完全断开时可能无法送达。正常关闭视频不报告错误；已捕获的诊断也保留在当前页面的“连接详情”中，刷新后不保留。

开发时可运行 `npm run test:wss-diagnostics:browser`，使用 FFmpeg 合成 H.264 与独立 Chromium 验证失败分类，不读取真实手机或生产视频。`CHROME_PATH` 和 `FFMPEG_PATH` 可覆盖测试程序路径。
